# Deep-research报告复核：WAM LR Ramp与Write LR×2短对照

日期：2026-10-26 UTC。用户要求先分析、再决定实施；本轮只读现有报告、日志、checkpoint header和训练代码，并记录计划。没有改变当前训练、配置、权重或进程。

## 建议

同一个2K optimizer-update完整状态分叉、先续训1K再决定是否延长至2K，是合理且值得优先的实验。两项中优先 **WAM LR Ramp**：它直接针对已有的首次WAM更新冲击，而且可以保持现有ZeRO参数组。Write LR×2是合理的第二候选，但不能仅凭原始梯度小断言其Adam更新不足，也不能保证gate会增大或最终成功率提升。

优先比较Control与Ramp-only；Ramp有信号后再比较Ramp+Write×2。若资源只能支持一轮快速筛选，可以Control对组合，但只能判断组合是否有用，不能归因两项各自收益。当前已启动的1%共享EA梯度退火实验保持独立，不中途换成报告的5%或临时叠加新策略。

### 对辅助梯度的判断不能只看cosine

Action–EA平均cosine接近0只排除了某些强方向冲突解释，不能排除幅值主导、有限容量分配或辅助目标与控制需求不完全一致。当前12k梯度比例来自少量重叠B1样本，不是最新正式batch32的Adam更新比。1%与5%都是候选，没有证据证明5%最优，也不能因报告偏好5%就中断已运行的1%实验。

报告赞成保留结构、用同起点短对照、固定噪声/场景、用Full/Off解释机制和补匹配Vanilla/No-EA，这些方向合理。外部相关工作的类比只构成动机，不保证本模型涨点；文内许多检索引用是不可直接解析的内部标记，不能替代本项目原始证据。

## WAM LR Ramp为什么优先，又为什么不是无代价

### 代码与日志支持的机制

现有WAM warmup保留完整前反向和global clipping，AdamW pre-hook只把WAM组grad置None，从而跳过参数、衰减和Adam状态更新。与此同时，原全局scheduler仍推进：其5% LR warmup只需1074次更新，早于WAM的2000次延迟更新结束。因此WAM第一次真正step时，LR已接近1e-4，Adam状态此前没有进行适配。

原成功run的实际边界：

| 微步/更新 | Action loss | 同步grad norm | 备注 |
|---|---:|---:|---|
| 4000/2000 | .014659 | .5531 | 最后一次WAM不更新 |
| 4002/2001 | .015430 | .6828 | 前向完成后首次WAM step，LR≈9.9498e-5 |
| 4003/2001 | .125502 | 非同步不记录 | 首次WAM step后的下一次前向 |
| 4004/2002 | .142266 | 12.5578 | 第二次联合更新 |
| 4006/2003 | .087127 | 4.2190 | 随后恢复 |

这与首次较大WAM更新造成瞬态扰动相符，构成Ramp的直接尝试依据；尚未通过干预证明唯一原因。

一个重要的验收细节：LR在梯度计算之后控制step，因此**同输入下首次联合反向的grad norm不会因降低LR自动变小**。应测FP32 master参数更新比例和随后几次前向的loss/clip，而不是要求首个gradient已降低。

### 固定一个简短候选

令u为前向前已经完成的optimizer updates。前2000次仍按原逻辑跳WAM Adam更新；从u=2000开始，WAM实际LR为原cosine当步LR乘以s：

s(u) = .1 + .9 × clamp((u−2000)/300, 0, 1)。

也就是约1e-5平滑升到原scheduled LR，300更新后回到原轨道。所有非Sidecar、且原来受WAM延迟更新控制的组一起处理，包括Action/Video/proprio等；Sidecar共享部分与heads的LR保持。Ramp期间WAM正常积累Adam状态，不额外冻结300步，也不重启整条cosine。

### 代价与限制

- 前300更新平均LR系数约.55，按原LR近似恒定估算，前1000更新的累计步长减少约13.5%。可能保护预训练能力，也可能使早期适配变慢。因此不能只因+500训练loss略高就否定，也不能只因曲线平滑就宣布提升。
- WAM变化更慢时，Sidecar相对WAM适配更快；组合Write×2后，初始Write LR约1e-4，而WAM只有约1e-5，形成约10倍的相对LR。两项并非自动抵消风险，需要实际对照。
- 原run已经恢复并获得正向SR，减少短暂尖峰可能不改变最终结果，甚至影响有利的早期适配轨迹。
- 一般warmup研究支持控制早期更新的动机，但收益依赖模型与优化状态，不构成本项目无代价提升的证明。[Why Warmup the Learning Rate?](https://arxiv.org/abs/2406.09405)

## Write LR×2：合理候选与具体工程约束

实际Write路径为`sidecar.stages.{0,1,2}.write.*`，包括query/LayerNorm/attention/output projection和beta，共36个参数张量、6,308,355个参数。EA heads共532,493参数。只提高Write的当步scheduled LR×2，Read/Refine/tokens/heads保持原LR；不修改前向、gate初始化或loss。

需要明确：提高学习率可能令gate更快缩小，也可能改进投影方向；不是承诺残差更大。Write本来就主要由Action/Video训练，EA到Write投影在现有观测隔离结构下为零。共享Read的EA梯度主导和Write映射优化不足是两种问题，不能用同一梯度比直接证明后者。Adam归一化也使“原始梯度小”不等于“参数更新小”。

### 报告示例不能原样落地

对当前checkpoint header按示例分类：`"sidecar.write" in name`只会抓到由`.beta`兜底命中的3个gate，漏掉其余33个Write张量；EA heads实际叫`sidecar.heads.*`，也不匹配示例的`ground_head/relation_head/plan_head`，会将全部532,493个heads参数误放WAM组。该问题属于报告的伪代码，不是当前训练已经使用了错误分组。

当前optimizer将整个Sidecar放在同一个组中，ZeRO-2再对其FP32 master与Adam moments做分区。直接新增Write参数组并调用旧`load_state_dict`可能报组数量/大小不匹配，或在不严谨映射时恢复错误状态。必须保留按名称/shape的模型映射、FP32 master、step、exp_avg、exp_avg_sq和scheduler，不能把重新初始化Write optimizer当作同一个LR对照。[PyTorch optimizer状态说明](https://docs.pytorch.org/docs/main/generated/torch.optim.Optimizer.state_dict.html)

Ramp保留现有分组，因此从旧state接续更容易。Write×2需选择可靠的ZeRO状态迁移，或经验证保持组结构的等效Write更新倍率方案；二者必须证明倍率1时下一步与原恢复一致、倍率2只改变Write当步更新，而不是拿梯度乘2代替LR乘2。当前尚未实现或验收这些改动。

若改变ZeRO分组，直接与Write候选比较的Control也应使用相同分组与迁移流程，Write倍率为1；或保持旧布局做经验证的等效实现。固定梯度下检查master/moments映射和更新数值，实际低精度reduction布局改变还可能带来舍入差异，不能只凭普通CPU优化器恢复成功就声称完整四卡逐位复现。

另一个现有scheduler细节：全部组共用绝对eta_min=1e-6。只改Write基准LR为1e-4，并沿用同一floor，后期Write/shared比会趋向1，并非始终2。若候选定义为`2×当步Sidecar LR`，应显式记录并保持这个定义；AdamW的有效weight decay步长也随LR一同改变，不能静默另调decay。

Ramp同样不能在每步把已修改的group LR继续乘系数，让递归cosine吸收该系数。应有原scheduled LR与effective LR的明确分离，在正确step位置应用并恢复，或使用组合scheduler；恢复后覆盖顺序也须验证。按optimizer计数而非微步/各rank内部scheduler.step计数执行。

## 同起点、短预算的具体实验

### 起点与单位

| 含义 | 累计optimizer updates | 累计microsteps/文件编号 |
|---|---:|---:|
| 2K warmup终点，分叉起点S | 2000 | 4000 |
| 分叉+250 | 2250 | 4500 |
| 分叉+500 | 2500 | 5000 |
| 分叉+1000，首轮决策 | 3000 | 6000 |
| 分叉+2000，必要时复核 | 4000 | 8000 |
| 原10epoch完整终点 | 21480 | 42960 |

不用等当前训练到4000次更新才有起点；4000微步就会保存2000更新的权重和`accel_state_step_4000`完整state。若等到4000更新之后才做分叉，也必须回到已固定的S，不能在4000更新的现有状态开始Ramp来声称测试了冷启动边界。

原成功run目录现仅有36000/40000微步的full state，原2K状态已不在该目录。可使用当前新run即将保存的S：前2K时其rho仍为1，前期策略未发生退火。所有短对照从**这一份实际S**恢复，不假定它逐位等于旧成功run的2K。

保存必须等`trainer_state.json`最终marker与全部ZeRO分片完整，再在独立目录固定S及其config/stats/contracts/tokenizer。keep_last_k=2可能在12000微步保存后清理4000状态，故应提前保护。只复制safetensors无法保留FP32 master/moments、scheduler/RNG和训练进度。

### 首选：EA保持原强度的LR对照

| 分支 | 共享EA梯度 | WAM Ramp | Write LR | 用途 |
|---|---|---|---|---|
| A Control | 1 | 无 | 1× | 同S、同预算基础对照 |
| B Ramp-only | 1 | .1→1，300更新 | 1× | 先检验最有直接依据的改动 |

先运行A/B到+1000；B有正向或稳定混合信号再决定延长+2000，并在Write状态迁移通过后考虑C。用户若更重视最快验证组合，可以只先跑A/C，但不能据此分别归因Ramp和Write的作用；之后补B即可分离组合增量。

若真正要测试“在当前1%方案之上加Ramp/Write”，也可将A/B/C全部设为相同rho1→.01；此时结论必须表述为1%方案下的增量，不能对照报告声称EA原监督不变。两种设定不能混表。

### 预算、保存与恢复

仍用四卡、bs32/acc2/global256、相同数据顺序策略、ColorJitter与10epoch/21480总更新cosine。按6.58秒/微步，+1000更新每臂约3.66小时，+2000约7.31小时；两臂串行分别约7.3/14.6小时，加载/保存/闭环另计，资源争用会改变实际耗时。

不能靠把num_epochs或max_steps改成短预算重建scheduler来做“同配方resume”；trainer会用它计算LR总周期。应保持原预算与已恢复的scheduler，用独立的优雅停止条件在目标更新结束后保存。

初筛可在+250/+500只保存部署权重，在+1000必须同时保存完整state，以便直接续至原10epoch总终点；不是再加10epoch。默认save_steps=4000微步不会自动给+1000位置的6000微步写full state，`finish_training`在非周期终点也只补最终权重；这点必须显式处理。+2000的8000微步则是原周期保存点。

若仅有当前GPU0–3这一组四卡，无法同时维持现有完整实验并并行两条新的四卡分支。先固定S，当前run照常；新的A/B需另一组四卡或明确后续排期，不能偷偷改当前run或误杀其他作业。

## 怎样判定短试值得继续

1. **前50–300更新，验工程与稳定性。** 检查每组scheduled/effective LR、WAM master实际更新、Adam状态正常推进、Action/Video/EA及clip。首个梯度应与同输入Control一致，WAM首个更新约乘.1；随后loss尖峰和clip是否减轻才是Ramp稳定性证据。Write若实现2×，应独立确认其当步更新、Read/heads未误加速。
2. **+1000时做一次固定离线比较。** 优先复用现有25GT/32FM作为开发诊断，固定noise，分Clean/Random、8/32步XYZ、SO(3)、gripper、Full/Off及真实write-r。先看候选Full是否比Control Full更好，再用Full/Off解释；Off变差也能制造更大的gap，不能把gap扩大当主目标。
3. **少量配对闭环是关键。** 预冻结三任务×双域×10场景=60条/模型，两模型共120条；保持相同accepted场景/指令/动作预算/推理噪声，不能只保证同一个seed整数。可继续使用现有三任务作为开发筛选，最后选型另用未参与选择的场景/更广任务验证。
4. **混合结果可延长至+2000再判断。** +1000主要是早期稳定性/方向筛选，不能保证最终排名，尤其Ramp减少了前期累计步长；原run约3.3K更新后已恢复，+2K终点更适合比较恢复后的持续差异。非有限/持续严重不稳定优先停候选；单batch或几次成功差不视为显著性。
5. **合格候选直接从自己的full state续到原预算。** 最终至少在相同32k和42960微步比较，保留最佳与最终，不能拿候选挑出的最好点只对照Control最后一点。匹配Vanilla/No-EA仍优先于继续增加第三、第四种trick。

本轮不再扩大Gate扫描、重新做大规模梯度分解或增加网络。报告的FP32 add若最后仍cast回BF16，并不能保证保住小于最终量化间隔的残差，且最新native/actual r已接近，不作为当前主候选；分组clip、main-task gain也分别是额外变量，先不叠。

60条筛选中一次成功就是1.67pp，每域30条的一次成功是3.33pp；因此适合排除明显退化，不足以证明期待的约2pp增益。若+1K阶段两组闭环都处于低成功率平台，应主要看工程健康并在+2K后复核，不用过早的floor结果判定最终排名。

2026-10-26T09:57:50Z实际进度3044微步/1522更新，最近100微步6.5929秒；剩约1.75小时到S，每臂+1K约3.663小时。四臂串行纯训练约14.65小时，连同当前剩余warmup约16.40小时；原估计3.7×4+1.5=16.3小时方向正确，但不包含加载、保存、实现/恢复验收和评估，也不保证资源持续独占。

此时间成立的前提是一组四卡能够在S完成后按计划串行执行四个短分支，或者另有四卡。若现有完整run仍占这组卡，新分支必须另排资源；本次讨论不构成自动停止当前run的执行。

### 为尽快提高最终效果，采用两级筛选

第一轮四个单项对照用于筛掉明显无效/有害候选，主要看候选Full相对A的固定输入Action误差和小型配对闭环，Full/Off与实际写回作为解释。B、C、D都不能只凭训练loss更平滑或gate更大入选。1K能判断早期方向，不能可靠预测32k/最终排名；若接近，优先让最有依据的前两组再续1K到累计4K更新，而不是在噪声中强行选赢家。
